# MADS Architecture Brief

**Repository:** `mads-msct` (master's thesis / "TFM", University project) · Python 3.11+
**Audience:** a new engineer or coding agent who needs to work in this codebase without first reading every Spanish doc.

## 1. Purpose and thesis goal

MADS ("Multi-Agent Data Science", the Spanish docs also gloss it as *Sistema Multiagente de Data Science auditable*) is a small, runnable skeleton of a multi-agent system that builds data-science pipelines with **governance, human approval, and verifiable traceability as first-class requirements** — not a production platform. The thesis argues that an agentic system doing analytical work (feature engineering, model selection, training, evaluation) can be trusted only if every step is authorized by a deterministic policy, is fully reproducible, and can be independently re-verified after the fact. The first applied domain is fraud/AML detection, but the architecture — contracts, policy packs as JSON, the Gate, the trace, the meta-auditor — is deliberately domain-agnostic; only one policy pack (`fraud_aml`) currently exists (`src/mads/policy_packs/fraude_aml.json`).

The core insight repeated throughout the docs: an LLM may *propose* an action, but only deterministic Python code — the risk classifier, the policy pack, and the Gate — may *authorize* it. Nothing the model outputs (a chosen action, a stated confidence, chain-of-thought) is ever treated as a permission grant.

## 2. Phased workflow

A case moves through five sequential phases: `UNDERSTANDING → PREPARATION → MODELING → EVALUATION → REPORTING`. A purely descriptive objective can skip straight from `UNDERSTANDING` to `REPORTING`. Within a phase there is no fixed recipe — the LLM chooses freely among whatever skills are technically available — but a closed phase hides its skills from the selector, and moving backward (`reopen_phase`) requires an explicit justification, human approval, a capped number of reopenings, and produces a new "analytical revision" that invalidates downstream evidence.

Each iteration of the loop is: observe state/evidence → compute technically available actions for the current phase → LLM selects exactly one action (structured output) → `PolicyGate` recomputes `allow`/`needs_approval`/`blocked` → a temporary worker executes one skill → state, versions, lineage, and invalidations update → loop. **Who decides what:** technical applicability (contracts + state) decides what can be *attempted*; the LLM decides which of those to *try*; the risk classifier decides the applicable risk; the `PolicyGate` is the sole authority that decides `allow`/`needs_approval`/`blocked`. A human is the approver for `needs_approval` (console prompt by default, injectable callable, `--auto-approve` for tests only). Final report generation is itself gated and requires a human decision.

`AgenticOrchestrator` (LangGraph, `src/mads/orchestrator/agentic.py`) is now the **only** way to run a case — `docs/orquestador-agentico.md` states this explicitly. It is a thin coordinator assembling eight small, independently testable, injectable components (each single-responsibility): `RunLifecycle`, `RiskCoordinator`, `ActionAvailabilityService`, `ActionSelector`, `AuthorizationCoordinator`, `ExecutionCoordinator`, `StateTransitionService`, `PhaseCoordinator`. The underlying LangGraph is a 3-node graph: `observe_and_select → gate_check → execute_action`.

## 3. What "skills" mean in MADS

**A "skill" in MADS is a data-science pipeline step, not an agent capability/tool-use "skill" in the Claude-Code sense.** Each skill (`src/mads/skills/*.py`) is a versioned, reusable, testable Python class implementing a `Skill` protocol (`skills/base.py`): it declares `skill_id`, `version`, `required_tools`, `produces` (artifacts), a `description`, and `risk_metadata` (technical facts only — data access, local/external effects, reversibility — **never** an authorization verdict). Examples: `validate_data`, `profile_data`, `propose_features`, `handle_missing_values`, `encode_categorical`, `engineer_features`, `treat_data`, `select_features`, `deduplicate_rows`, `split_data`, `baseline_model`, `cross_validate_models`, `select_model`, `tune_hyperparameters`, `train_model`, `evaluate_model`, `generate_analytical_report`.

The **registry** (`skills/registry.py`, `default_skill_registry()`) is the versioned catalog of capabilities; each skill also has a small `SkillContract` describing technical requirements, applicability, produced artifacts, state mutations, invalidation rules, and repetition rules. `calculate_available_actions()` (`orchestrator/actions.py`) evaluates these contracts against current state deterministically to produce the set the LLM is allowed to choose from — the LLM never sees or picks anything outside this computed set. **Authorization** is a separate downstream step: the policy pack maps risk + skill risk facts to a verdict, and the `PolicyGate` recomputes that verdict independently right before execution, never trusting a cached authorization. `mads catalog` prints the registered capabilities; `mads skills` / `mads skills show <id>` explore them via the read-only console.

## 4. Worker/agent roles

- **`RiskClassifier`** (`risk.py`): the single LLM-backed classifier. Runs once, before the graph, on the untrusted `Case` JSON; produces a `RiskAssessment` (risk level, category, confidence, inconsistencies, human-review flag). It classifies — it never authorizes.
- **`ActionSelector`** (`orchestrator/selection.py`): builds the prompt/schema, calls the LLM, validates the single proposed action. Has no access to workers, a mutable `ArtifactStore`, or `PolicyGate` — an invalid or out-of-set proposal never reaches execution.
- **`PolicyGate`** (`gate.py`): the sole authorization checkpoint. Recomputes the verdict from the `RiskAssessment` it was constructed with (never from `case.risk_level`, the user-declared/non-authoritative value). Approver is an injectable callable.
- **`SkillWorker`** (`workers/base.py`): a temporary container created per task, holding exactly the tools it was granted; raises `PermissionError` if a skill needs an ungranted tool; discarded after execution.
- **Decision resolvers** (`decisions.py`): separate channel for *analytical* preferences (e.g., how to impute a column, which algorithm family) — `AutomaticDecisionResolver` (tests/CI), `llm` (unsupervised), `llm-confirm` (LLM proposes, human must confirm — the default for interactive runs). These never substitute for Gate authorization.

## 5. Audit and assurance layer

Six mechanisms, layered: (1) versioned normative sources (`compliance/fuentes.md`, stable `source_id`s, e.g. `ai-act-2024`, `rgpd-2016`, `aepd-guias`); (2) a requirement→technical-control map (`compliance/mapeo_requisitos_controles.json`) tying e.g. AI Act art. 12 (event logging) → the hash-chained trace, art. 14 (human oversight) → Gate's `needs_approval`, RGPD art. 9 (special-category data) → policy rule `AML-002`; (3) deterministic policy packs (JSON, evaluated in rule order, conservative default `needs_approval`); (4) a not-yet-implemented normative RAG (`src/mads/rag/contracts.py` — contract only, deliberately incapable of returning a `Verdict`, purely for future evidence citations); (5) human review, encoded as Gate `needs_approval` plus `approval_requested`/`human_response` trace events.

The **meta-auditor** (`audit/meta_auditor.py`, plus `audit/extended_controls.py` for A14/A16/A17/A18 and `audit/provenance.py` for environment capture) runs automatically after `case_finished` and re-derives 18 deterministic controls (A1–A18) purely from the already-written trace and artifact manifest — it never trusts the orchestrator's own success flags. Highlights: A1 (hash-chain integrity), A3/A4 (execution without/after a valid gate decision), A5/A10 (missing or mismatched evidence — double-checked against both events and manifest), A11/A12/A14 (train/test partition integrity and no leakage), A13 (independent re-derivation of model selection), A15 (execution ordering vs. risk classification), A16 (Gate decision reproduced against the frozen policy snapshot), A17 (provenance of case/dataset/code/dependencies/seeds), A18 (report content matches source artifacts). `mads audit <run_dir>` re-runs this independently; results are `passed`/`passed_with_warnings`/`failed` overall, with a per-control status. Output artifacts `audit_report.json` and `assurance_report.md` are written to the run root — not inside `artifacts/` — specifically to avoid a circular dependency in the manifest being audited.

## 6. Tracing and run artifacts

Every event in `trace.jsonl` is hash-chained (`hash = sha256(canonical_json(event minus hash))`, `prev_hash` links to the previous event); `mads verify <run_dir>` recomputes the whole chain in O(n), statelessly. Justification is always structured (`decision_code` + `criteria` + `alternatives_considered` + `evidence_refs`) — **chain-of-thought is never persisted**, and any traced prompt/response is redacted (`utils.redact`) for secrets/PII first. A run directory (`runs/<name>/`) contains: `trace.jsonl` (append-only event log), `audit_report.json`, `assurance_report.md` at the root, and an `artifacts/` folder holding `manifest.json` (sha256 per file), `policy_snapshot.json`, `run_environment.json`, `report_facts.json`, `analytical_decisions.json`, `case_report.md`, and the pipeline's per-skill artifacts (`data_validation.json`, `data_profile.json`, `data_split.json`, `model.joblib`/`model.json`, `evaluation.json`, etc.). Overwritten stable-named artifacts are archived under `artifacts/.history/`, never deleted. `mads run` refuses to reuse a non-empty output directory unless `--force` is passed.

## 7. CLI commands and the console

`mads` (entry point `mads.cli:main`) exposes: `run <case.json> --output <dir>` (executes a case; requires `--decision-actor-id`/`--decision-actor-role` or prompts for them), `verify <run_dir>`, `audit <run_dir>`, `catalog`, `skills` / `skills show <id>`, `runs` (list discovered runs under `runs/`), `status [<run_dir>]` (defaults to the latest run), and `llm-test [--model ...]` (connectivity check). Exit codes are stable: `0` success, `1` a failed run/verify/audit/connection, `2` invalid args/env/case/policy-pack/config. The **console** (`src/mads/console.py`) is a purely observational, read-only presentation layer added recently (`skills`/`runs`/`status`): it reads already-written `trace.jsonl`/`manifest.json`/artifacts and the skill registry, tolerates missing/corrupt files by returning partial data plus warnings, and never instantiates or drives `ActionSelector`/`PolicyGate`/orchestrator internals.

## 8. LLM access via LiteLLM

LiteLLM is the **only** LLM integration layer; `LiteLLMProvider` (`src/mads/llm/litellm_provider.py`) is the sole production implementation of the `LLMProvider` protocol (`complete`/`complete_structured` → `LLMResponse`). No module imports LiteLLM directly except this provider, and no other SDK is wired in. Configuration: put `OPENAI_API_KEY=`/`ANTHROPIC_API_KEY=` in `.env` (LiteLLM reads these directly; MADS never processes, stores, or logs them). Model selection priority: `--model <litellm-id>` flag, then `MADS_MODEL` env var (a MADS-specific convention, not native to LiteLLM), then the default `gpt-5.6-luna`. A bare name implies OpenAI; `"<provider>/<model>"` routes elsewhere (e.g. `anthropic/claude-sonnet-4-5`). Each `llm_call` trace event records `provider`/`model` (the real responder), `model_requested`, redacted prompt/output, tokens, and cost (via `litellm.completion_cost`; `None` rather than a guessed number when unpriced). By design there is no fallback, no MADS-driven retry, and no response cache in this integration.

## 9. Datasets and example cases

`examples/cases/*.json` are demo `Case` definitions (JSON, "untrusted input"): `caso_credito_aleman_arbol.json` (German credit risk, decision tree, sensitive attribute `personal_status_sex`), plus `caso_credito_aleman.json`, `caso_creditcard_fraude_001.json`, `caso_energia_regresion_001.json`, `caso_titanic_3.json`. `data/` holds the matching synthetic/demo CSVs (e.g. `credito_aleman.csv`); the README stresses these are synthetic and for demonstration only. A `Case` declares `objective`, `domain`, `dataset_path`, `target`, `features`, `sensitive_attributes`, a user-declared (non-authoritative) `risk_level`, `affects_natural_persons`, optional `risk_context` and `modeling_config` (task type, algorithm/family, CV folds, seed, class balancing, hyperparameter tuning).

## 10. Current state and roadmap

`docs/estado-tfm-11-ago.md` (dated 11 Aug 2026) is a **snapshot mid-integration**, not the current state — see §12 below for how it now diverges from the code/docs on `main`/`mario-harnes`. At that snapshot: risk classification, the LangGraph agentic orchestrator, `treat_data` redesign, and LiteLLM/cost accounting were on separate feature branches (`dev`, `cgt-integracion-langgraph`, `adrian-cambias`) awaiting a specific merge order; A1–A16 controls existed with A15 "being added." The catalog held 34 algorithms across 7 families. Not-yet-built, explicitly out of scope unless the team decides otherwise: a visualization skill, SHAP explainability, formal fairness metrics, the normative RAG, and a "model improvement" reactive loop. Turning this into a production product (login, DB, API, frontend) is explicitly **not** a thesis requirement. The largest stated risk at that time was the thesis write-up lagging the code, with submission due mid-September 2026.

## 11. Known limitations and design decisions

From `docs/referencias-adoptadas.md`: MADS synthesizes ideas from three reference projects — the Gate/policy-pack/meta-auditor pattern from "Nucleo," the hash chain/typed work-orders/artifact manifest from "tfm-mario," and the capability-catalog/routing-as-documented-decision idea from "TFM-Arquitectura-Lucas" — while explicitly discarding each project's heavier machinery (execution sandboxes, YAML policies, cross-case global checks, JSON-Schema validation, agent-packs/playbooks/MCP wrappers) as unnecessary complexity for a one-month thesis scope. From `docs/decisiones-analiticas.md` and elsewhere, explicit known limits: PII redaction is regex-based and not infallible; the hash chain detects tampering but cannot prevent someone with write access from regenerating a whole new valid-looking chain; LLM-produced confidence is uncalibrated and never grants permission on its own; the test suite's deterministic LLM double establishes a baseline, not general reliability of a remote model; declared actor identity/role is unauthenticated (no SSO/corporate identity provider yet); human confirmation in `llm-confirm` mode is synchronous only (no pause/resume across processes); and the entire normative layer is explicitly *not* legal advice or a compliance guarantee.

## (b) User-facing string locations needing translation (categories)

- **Prose documentation** — all files under `docs/`, `README.md`, `compliance/*.md`: full narrative Spanish, largest volume.
- **CLI help/usage text and prompts** — `argparse` help strings, subcommand descriptions, and interactive prompts in `src/mads/cli.py` (e.g. actor id/role prompts, risk-context follow-up questions) and console output strings in `src/mads/console.py` (phase display names like `"Comprensión"`, status labels, table headers).
- **Runtime/error messages** — exceptions and validation failures raised across `src/mads/*.py` and `src/mads/skills/*.py` (e.g. structural validation failures in `validate_data`, algorithm/config errors), since these surface directly to the CLI user.
- **Policy pack content** — human-readable fields inside `src/mads/policy_packs/*.json`: `description`, `reason` strings (JSON *keys* like `rule_id`, `verdict`, `action_types` are stable identifiers and should **not** be translated, only the prose values).
- **Compliance mapping content** — descriptive text fields (`requirement`, `technical_control`, `evidence`) inside `compliance/mapeo_requisitos_controles.json` and the source table in `compliance/fuentes.md` (keep `source_id`s and legal citations stable).
- **Analytical decision text** — question/reason/alternative strings generated in `decisions.py` and per-skill decision-request builders (e.g. `treat_data`, `handle_missing_values`, `propose_features`), since these are shown to a human approver.
- **Generated reports** — narrative text produced by `generate_analytical_report` into `case_report.md`, and any human-readable summaries inside `assurance_report.md`.
- **Example case content** — free-text fields inside `examples/cases/*.json`, chiefly `objective` and the `risk_context` sub-fields (`intended_use`, `decision_role`, etc.); structural keys should stay as-is since they are the JSON schema.
- **Code comments and docstrings** — extensive Spanish inline documentation throughout `src/mads/**/*.py`, not user-facing at runtime but relevant for future contributor-facing translation.
- **Test fixture strings** — Spanish objective/PII text embedded in `tests/*.py` used to exercise redaction and validation; lower priority since not shipped, but relevant if tests move to English test names/fixtures for consistency.

## (c) Contradictions / outdated documentation found

1. **Single vs. dual orchestrator.** `docs/orquestador-agentico.md:3-4` states plainly: *"`AgenticOrchestrator` es la única forma de ejecutar un caso en MADS... no ofrece una selección de modo."* But `docs/estado-tfm-11-ago.md:41-45` describes a live CLI dimension `Orquestador: normal (planifica todo una vez) / agentic (LangGraph, paso a paso)` as a currently-supported choice. The `estado-tfm` document is a dated point-in-time integration snapshot (11 Aug 2026) that predates the merge collapsing to a single agentic orchestrator; it should be labeled historical or removed from onboarding paths, since a new reader following it would expect a `--orchestrator` flag that does not exist in the current CLI (`src/mads/cli.py`, confirmed via `argparse` subcommands: `run`, `verify`, `audit`, `catalog`, `skills`, `runs`, `status`, `llm-test` — no orchestrator-mode flag).
2. **Meta-auditor control count.** `docs/estado-tfm-11-ago.md:13` says "Meta-auditor con controles A1-A16 (ampliándose ahora mismo con A15...)". Current code and current docs both go further: `docs/trazabilidad.md:99-118` documents A1–A18, and `src/mads/audit/extended_controls.py` implements A16, A17, and A18 directly (confirmed by grep). The estado doc is stale on this count too.
3. **LLM provider integration.** `docs/estado-tfm-11-ago.md:28,43` describes per-call OpenAI/Anthropic cost tracking and a CLI `--provider openai|anthropic` dimension as the current mechanism. This has since been replaced wholesale: the most recent commit on this branch is *"feat(llm): sustituir OpenAI/Anthropic por LiteLLM como única integración"*, and `docs/litellm.md` / `README.md:40-55` now describe LiteLLM as the sole integration, selected via a `--model <litellm-id>` identifier or `MADS_MODEL`, not a `--provider` flag. `estado-tfm-11-ago.md` predates this migration and should not be used to infer current CLI flags.
4. **Branch/merge-plan section is orphaned.** Sections 3–4 of `docs/estado-tfm-11-ago.md` (branch status table, merge order recommendation for `dev`/`cgt-integracion-langgraph`/`adrian-cambios`) describe a coordination plan for branches that, per `git branch -a`, still exist as remotes (`origin/dev`, `origin/cgt-integracion-langgraph`, etc.) but whose described content (dual orchestrator, per-provider cost tracking) is already superseded on the current branch (`mario-harnes`, off `main`) by the 8-component orchestrator refactor and the LiteLLM migration — i.e., either those branches were already reconciled differently than the doc's plan, or the doc is simply stale. A reader should not treat this section as an accurate description of current integration status without checking `git log`/branch diffs directly.
5. **Minor: `README.md` code map** (`README.md:293`) lists `docs/skills.md` scope as "cómo se separan skills y workers temporales," which undersells the file's actual (and much larger, 1051-line) content — it is the canonical reference for nearly every data-preparation and modeling skill's exact algorithm, leakage-prevention, and artifact contract, not just the skill/worker separation. Not a factual contradiction, just a description that will mislead a reader into skimming past the file's real value.
6. **Terminology note, not a contradiction:** the domain word "expediente" the task prompt anticipated as a formal term does not appear as one anywhere in `src/mads/` or `docs/` — it only shows up as example PII-laden text inside two test fixtures (`tests/test_cli_modeling_choice.py:351`, `tests/test_policies_gate.py:236`) used to exercise redaction. The system's actual unit-of-work term throughout is `caso`/`Case`, not `expediente`.
